# Competitive gap and scope decision

CrowdForge's defensible advantage is **audience terrain changes with inspectable safety decisions and reproducible round evidence**. BFS itself is not novel. The value is the complete transaction: count an eligible vote, select a deterministic proposal, validate it, commit atomically, explain the result, and replay the state. The comparison is against explicit baselines, not claims about unexamined competing entries.

| Candidate | At audit start | Decision and residual gap |
|---|---|---|
| A. Integrity Engine 2.0 | Safe reachability, lava buffer, immutable entities, atomic changes, basic replay/reasons existed. | **Implement:** duplicate-target conflict rejection, path-length/exposure analysis, 12-step detour cap, remaining-time check, before/after tile evidence. Exposure is adjacency on one deterministic shortest safe route, not a danger model or predicted damage. Single writer avoids overlapping concurrent commits; no distributed conflict protocol is claimed. |
| B. Adaptive Chaos Director | Fixed mutations; seeded distance-based target selection; no adaptive controller. | **Defer:** HP/time-driven interventions risk secretly overriding viewers and require balance testing. Bounds now constrain proposals, but that is not an adaptive director. Route-aware targeting is a promising next product experiment after audience feedback. |
| C. Audience Factions | Lava/wall opposition and bridge support; no faction membership/resources. | **Defer:** resources, joining/switching, cooldowns, UI explanations and exploitation rules add substantial complexity. Calling existing choices “factions” would be cosmetic and misleading. |
| D. Audience Impact Replay | Aggregate recorded inputs + CLI verification + event list. | **Implement:** replayed mode changes, stronger digest, owner-only in-app proof, tile diffs and preserved v1 rules. **Defer:** cinematic scrubber/full map playback and event-store recovery. The database stores snapshots of input logs, not a distributed event-sourcing system. |
| E. Streamer Experience | Original pixel art, actual play, observer scene, help/controls. | **Implement:** short authoritative movement interpolation, damage border, final-three-second forging cue, keyboard-contained dialogs and mobile diagnostics entry. Preserve low-motion behavior. **Defer:** new maps/progression/music/art rewrite. |
| F. Reliability | OAuth protections, refresh, EventSub handoff/dedup, snapshot resync, Docker CI. | **Implement:** no unsolicited client pings; real receipt counters; monotonic snapshot sequence; checkpoint fault isolation; eight-observer reset/reconnect test. **Remaining:** real-account soak/rehearsal, reverse proxy/public deployment verification, restore-after-crash, internet abuse limits. |

The largest unresolved product weakness is pacing: the fixed safe corridor can be escaped before the first vote, and there is no measured replayability or retention. Shortening windows or introducing a portal lock would alter fairness and require fresh live playtesting. We deliberately avoid such a late rule change without community feedback. A rehearsed demo must let viewers influence a genuine run without presenting staged waits as natural retention evidence.

No runtime LLM, database replacement, distributed service, new engine or dependency was added. The game remains one authoritative Python process with React/Canvas rendering. This improves the strongest component within the remaining calendar time; it does not establish a guaranteed finalist advantage.
